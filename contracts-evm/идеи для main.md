# Идеи для будущих поколений (Ga_2 и далее)

В этот документ заносятся перспективные архитектурные идеи, оптимизации и механизмы, которые решено отложить до следующих поколений контрактов, чтобы не усложнять и не раздувать текущее стабильное ядро `InfinityVerse_Main_Ga_1`.

---

## 1. SSTORE2 / Байткодное хранилище неизменяемых BLOB-данных
- **Суть идеи:** Использование паттерна `SSTORE2` (запись неизменяемых BLOB-данных произвольного размера напрямую в байткод дочерних контрактов через `create` / `create2` с последующим чтением через `extcodecopy`).
- **Зачем:** Для больших статических файлов (карты, текстуры, логи, большие JSON-состояния) `SSTORE2` обходится значительно дешевле обычного `sstore` в слоты памяти (затраты снижаются с 20 000 газа за 32 байта до ~200 газа за байт при деплое кода).
- **Почему отложено:** В текущем поколении `Ga_1` универсального динамического маппинга `mapping(bytes32 => bytes) blobs` достаточно для всех оперативных задач, а внедрение фабрики дочерних контрактов и деплой кода через ассемблер усложняет аудит безопасности.

---

## 2. Ончейн Мультиплексор / Сканер поколений (Archive Scanner & Cross-Gen Finder)
- **Суть идеи:** Встроенный view-метод для поиска данных игрока/секторов вглубь истории по всем поколениям:
  ```solidity
  function findLatestSector(bytes32 sector) external view returns (bytes32 val, uint256 foundInGen, address contractAddr);
  ```
  Метод сканирует поколения от текущего (`totalGenerations`) назад к 1 и возвращает первое непустое значение.
- **Вторая вариация:** `getSectorHistory(bytes32 sector)` — возвращает срез значений сектора по всем эпохам.
- **Почему отложено:** Сейчас поколение Ga_1 только запускается (история пока состоит из 1 поколения). В текущем ядре уже есть быстрый доступ ко всем адресам `getAllGenerations()` и `getGeneration(i)`. При необходимости глубокого анализа поколений лучше создать внешний отдельный Lens-контракт (`InfinityVerse_HistoryLens`), чтобы не тратить лимит размера главного контракта.

---

## 3. Наследуемый указатель на последнее активное поколение (Lazy Pointer)
- **Суть идеи:** При первой миграции или действии игрока в новом поколении в его сектор упаковывать ссылку `lastSeenGen: N`.
- **Зачем:** Чтобы при поиске исторических данных модуль сразу обращался к нужному поколению через `getGeneration(N)` без перебора промежуточных неактивных эпох.
- **Почему отложено:** Логика упаковки специфична для игровых модулей (например, модуля логики `AAA`) и не должна жестко зашиваться в универсальный диск `Main`.

---

## 4. ERC-20 / Native Token Hook / Receiver Callbacks (EIP-1363 / ERC-777 style)
- **Суть идеи:** Возможность автоматического вызова обработчика при поступлении токенов или ETH в хранилище с передачей прав доверенным модулям.
- **Почему отложено:** В `Ga_1` уже есть функции экстренного спасения `rescueERC20` и `rescueETH` под защитой `CLEARANCE_2`. Любая сложная токеномика должна реализовываться во внешних модулях, а не в ядре хранилища.
